# Техническое описание логики

Данный документ описывает внутреннее устройство и алгоритмы работы скрипта `ssh_key_manager.py`.

---

## 1. Архитектура

Скрипт построен по функциональному принципу. Каждая функция отвечает за свою задачу.

| Функция | Назначение |
|---|---|
| `main()` | Точка входа. Загрузка конфигурации, оркестрация обработки серверов. |
| `connect_and_setup_ssh()` | Полный цикл: проверка ключа → пароль → генерация → деплой на сервер. |
| `execute_remote_command()` | Выполнение команды на удалённом сервере с ожиданием завершения. |
| `log()` | Форматированный вывод с цветами и временными метками. |
| `enable_windows_ansi()` | Активация ANSI-цветов в консоли Windows. |
| `test_connection()` | Проверка соединения командой `ls -la /`. |
| `disconnect_ssh()` | Корректное закрытие SSH-сессии. |

---

## 2. main()

**Загрузка конфигурации:**
- Определяется путь к скрипту через `__file__`.
- Имя конфига вычисляется как `{имя_скрипта}.cfg`.
- Если файл не существует — создаётся шаблон с уже сгенерированным UUID, скрипт завершается.
- Если существует — читается JSON.

**UUID:**
- При создании шаблона UUID4 генерируется сразу.
- При чтении: если `uuid` равен `null` (администратор сбросил вручную) — генерируется новый UUID и записывается в конфиг.
- UUID используется как идентификатор экземпляра скрипта во всех комментариях ключей.

**Определение путей:**
- `local_key_dir` — из конфига. Если `null` — папка `ssh_keys` рядом со скриптом.

**Цикл обработки серверов:**
1. Проверка `enabled`. Если `false` — пропуск с сообщением.
2. Проверка `host`. Если отсутствует — пропуск с предупреждением.
3. Вызов `connect_and_setup_ssh()` с параметрами сервера.
4. Вызов `test_connection()`.
5. Вызов `disconnect_ssh()` в `finally`.
6. Сбор ошибок в `failed_servers`.

**Сводка:**
- Если есть ошибки — вывод списка с описанием, выход с кодом 1.
- Если всё успешно — `[OK] Все серверы обработаны успешно!`, выход с кодом 0.

---

## 3. connect_and_setup_ssh()

Основная функция. Принимает: `host`, `username`, `password`, `local_key_dir`, `remote_home_dir`, `instance_id`, `server_name`, `key_size`.

**Шаг 1. Формирование имени ключа:**
- Если задан `server_name` — используется он.
- Иначе — `host` с заменой точек на подчёркивания.
- Имя файла: `id_rsa_{имя}`.

**Шаг 2. Попытка входа по ключу:**
- Проверяется наличие приватного ключа на локальной машине.
- Если есть — попытка `ssh.connect()` с параметром `key_filename`.
- Успех — возврат сессии, работа завершена.
- `AuthenticationException` — переход к шагу 3.
- Сетевая ошибка — исключение пробрасывается наверх.

**Шаг 3. Аутентификация по паролю:**
- Если пароль задан в конфиге — попытка входа.
- Не подошёл или отсутствует — интерактивный ввод через `getpass`.
- Ошибка — исключение.

**Шаг 4. Генерация новой пары ключей:**
- Если старый ключ существовал — предупреждение о замене.
- `paramiko.RSAKey.generate(key_size)` — генерация с переданным размером.
- Сохранение приватного ключа через `write_private_key_file()` (формат OpenSSH).
- Установка прав `600` на приватный ключ.
- Формирование строки публичного ключа: `{тип} {base64} {user}@{host}:{server_name}:{uuid}`.
- Сохранение публичного ключа в `.pub` файл.

**Шаг 5. Деплой на сервер:**
- Проверка существования `~/.ssh`. Если нет — создание с `chmod 700`.
- Проверка существования `authorized_keys`. Если нет — создание с `chmod 600`.
- Если файлы уже существуют — права не меняются.
- Чтение текущего содержимого `authorized_keys`.

**Шаг 6. Анализ и очистка старых ключей:**
- Поиск строк, содержащих `{user}@{host}:{server_name}:`.
- Строки с текущим `instance_id` и точным совпадением ключа — оставляются.
- Строки с текущим `instance_id`, но другим ключом — помечаются как старые.
- Строки с другим `instance_id` — помечаются как старые.
- Если старые ключи найдены — интерактивный запрос на удаление (`y/n`).
- Чужие строки (без паттерна) — сохраняются.

**Шаг 7. Добавление актуального ключа:**
- Если точного совпадения не было — новая строка добавляется.

**Шаг 8. Бэкап и запись:**
- Создание резервной копии: `cp authorized_keys authorized_keys.bak.YYYY-MM-DD_HH-MM-SS`.
- Полная перезапись файла через `cat >` с передачей содержимого через stdin.

---

## 4. Генерация ключей

- **Метод:** `paramiko.RSAKey.generate(key_size)`.
- **Длина по умолчанию:** 3072 бит (глобальная константа `KEY_SIZE`).
- **Переопределение:** поле `key_size` в конфигурации сервера.
- **Допустимые значения:** 2048, 3072, 4096.

| Биты | Описание |
|---|---|
| 2048 | Слабо. Не рекомендуется. |
| 3072 | Стандарт. Рекомендовано для большинства случаев. |
| 4096 | Сверхнадёжно. Дольше генерируется. |

- **Формат сохранения:** `write_private_key_file()` записывает в формате OpenSSH (`-----BEGIN OPENSSH PRIVATE KEY-----`). Это формат, который Paramiko 4.0.0 читает при последующих запусках.

---

## 5. Деплой ключа

**Проверка окружения:**
- `test -d ~/.ssh` — существует ли директория.
- Если нет: `mkdir -p` + `chmod 700`.
- `test -f authorized_keys` — существует ли файл.
- Если нет: `touch` + `chmod 600`.
- Если существуют — права не меняются (защита от поломки симлинков Proxmox).

**Анализ строк:**
- Чтение всего файла через `cat`.
- Разбивка на строки.
- Поиск по паттерну `{user}@{host}:{server_name}:`.

**Логика классификации строк:**

| Условие | Действие |
|---|---|
| Содержит паттерн + текущий UUID + точное совпадение ключа | Оставить (актуальный ключ) |
| Содержит паттерн + текущий UUID + другой ключ | Пометить старым |
| Содержит паттерн + другой UUID | Пометить старым |
| Не содержит паттерн | Оставить (чужой ключ) |

**Интерактивный запрос:**
- Если найдены старые ключи — вывод количества и запрос `[?] Удалить их? (y/n):`.
- `y` — старые исключаются из списка.
- `n` — старые остаются.

**Бэкап:**
- `cp authorized_keys authorized_keys.bak.YYYY-MM-DD_HH-MM-SS`.
- Создаётся перед каждой перезаписью.

**Запись:**
- Все оставшиеся строки + новая строка (если добавляется) склеиваются через `\n`.
- Передаются в `cat > authorized_keys` через stdin.
- Полная перезапись файла.

## 6. UUID и идентификация

**Генерация:**
- UUID версии 4 (случайный).
- Создаётся при первом запуске, сохраняется в `ssh_key_manager.cfg`.
- Если администратор заменил `uuid` на `null` — при следующем запуске генерируется новый.

**Формат комментария ключа:**
```
{username}@{host}:{server_name}:{uuid}
```
Пример: `root@192.168.87.15:Proxmox-Main:a1b2c3d4-e5f6-7890-abcd-ef1234567890`

**Поиск своих ключей на сервере:**
- Скрипт ищет строки с паттерном `{user}@{host}:{server_name}:`.
- UUID позволяет отличить ключи текущего экземпляра от ключей других копий скрипта.
- При одинаковом UUID, но разном ключе — определяется, что ключ был перегенерирован (старый помечается).

## 7. execute_remote_command()

- Принимает: `ssh` (сессия), `command` (строка), `description` (опционально).
- Если передано описание — логирует его.
- Логирует саму команду ярко-зелёным цветом.
- Выполняет `ssh.exec_command(command)`.
- Вызывает `stdout.channel.recv_exit_status()` — принудительное ожидание завершения.
- Возвращает кортеж: `(exit_status, stdout, stderr)`.

---

## 8. log()

- Принимает: `prefix` (префикс), `message` (сообщение), `msg_color` (опциональный цвет сообщения).
- Формирует временную метку `[HH:MM:SS]`.
- При `USE_COLORS = True`:
  - Временная метка — ярко-белый.
  - Префикс — цвет из словаря `PREFIX_COLORS`.
  - Сообщение — опциональный цвет.
  - После каждого цветного элемента — сброс `CLR_RESET`.
- При `USE_COLORS = False` — вывод без ANSI-кодов.

**Словарь цветов префиксов:**

| Префикс | Цвет | Назначение |
|---|---|---|
| `[OK]` | Зелёный | Успех |
| `[X]` | Красный | Ошибка |
| `[i]` | Голубой | Информация |
| `[!]` | Жёлтый | Предупреждение |
| `[...]` | Синий | Процесс |
| `>>>` | Голубой | Начало этапа |
| `---` | Серый | Разделитель |
| `***` | Жёлтый | Важное |
| `===` | Ярко-белый | Заголовок |
| ` ` (пробел) | Серый | Вывод команды |

---

## 9. enable_windows_ansi()

- Проверяет, включён ли `USE_COLORS` и является ли платформа Windows.
- Через `ctypes.windll.kernel32` получает дескриптор stdout.
- Читает текущий режим консоли.
- Добавляет флаг `ENABLE_VIRTUAL_TERMINAL_PROCESSING` (0x0004).
- При неудаче — возвращает `False`, скрипт продолжит работу без цветов.

---

## 10. test_connection()

- Выполняет `ls -la /` на сервере.
- При успехе — построчно выводит результат серым цветом.
- При ошибке — читает stderr и выбрасывает исключение.

---

## 11. disconnect_ssh()

- Вызывает `ssh_session.close()`.
- Логирует завершение.

---

## 12. Режим --show

- Активируется флагом `--show` в командной строке.
- Выполняется до основного цикла обработки.
- Для каждого сервера с `enabled: true`:
  - Проверяет наличие локального ключа.
  - Пытается подключиться.
  - Выводит статус: доступен / ключ не найден / аутентификация отклонена / ошибка.
- Не запрашивает пароль, не генерирует ключи, не меняет файлы на сервере.
- После проверки всех серверов — выход с кодом 0.

---

## 13. Бэкап

- Создаётся в `connect_and_setup_ssh()` перед записью `authorized_keys`.
- Команда: `cp {auth_keys} {auth_keys}.bak.{timestamp}`.
- Формат метки: `YYYY-MM-DD_HH-MM-SS`.
- Бэкапы копятся в `~/.ssh/` на сервере. Администратор может чистить их вручную.

---

## 14. Обработка ошибок

| Уровень | Исключение | Действие |
|---|---|---|
| `connect_and_setup_ssh()` | `AuthenticationException` | Переход к следующему методу аутентификации |
| `connect_and_setup_ssh()` | `SSHException`, сетевая ошибка | Проброс наверх |
| `main()`, цикл обработки | Любое исключение | Логирование, добавление в `failed_servers`, переход к следующему серверу |
| `main()`, чтение конфига | Ошибка парсинга JSON | Завершение скрипта с кодом 1 |
| `main()`, запись конфига | Ошибка записи | Завершение скрипта с кодом 1 |
